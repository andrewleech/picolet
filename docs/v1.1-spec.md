# Picolet v1.1 Specification — Examples Epic

This document is the contract for v1.1: real worked-example apps plus
the autonomous test / remote-control infrastructure that makes them
demonstrable and testable.

Frame inputs:
- v1 spec at [v1-spec.md](v1-spec.md) defines the framework FR/NFR.
- v1 acceptance audit at [V1_ACCEPTANCE_AUDIT.md](V1_ACCEPTANCE_AUDIT.md)
  is approved-with-conditions; carryover items feed v1.1 backlog.
- The "real examples" question surfaced post-review:
  `hello-webview` is a two-button toy, not an app.

## Targets

Same as v1: `linux-x64`, `windows-x64`. macOS/ARM still out of scope.

## Functional requirements

### Autonomous test + remote-control

| ID | Requirement |
|---|---|
| FR-TEST-1 | Each webview runtime variant accepts `PICOLET_TEST_MODE=1` and exposes the underlying engine's debugging protocol on a runtime-chosen port. Port is announced via `picolet:test-port=<N>` line on stderr at startup. |
| FR-TEST-2 | The LVGL runtime variant exposes a Python-side `picolet._test` API (registered when `PICOLET_TEST_MODE=1`) that synthesises pointer + key events to widgets and captures the LVGL display buffer to a PNG. |
| FR-TEST-3 | `picolet test [--browser webkit\|chromium] <binary>` runs the app under Playwright with the debugging port pre-attached. Returns a Playwright `Page` handle. The CLI is the entry point Python test code calls into. |
| FR-TEST-4 | `picolet test --screenshot <png-path> <binary>` builds the app (if needed), launches it, waits for the page-ready signal, captures a PNG, terminates the app. Headless via xvfb on Linux; native window on Windows (WSL interop). |
| FR-TEST-5 | A Python helper `picolet.testing.AppHarness` wraps the test workflow: spawn → wait-ready → drive → assert → terminate. Used by example apps' integration tests + by example test plans. |
| FR-TEST-6 | LVGL example apps' tests use the same harness shape, swapping the Playwright driver for the LVGL-side `_test` API. |

### Vue.js + Vite toolchain

| ID | Requirement |
|---|---|
| FR-VUE-1 | `picolet init <name> --template hello-vue` produces a working Vue 3 + Vite + TypeScript app skeleton that builds via `picolet build`. |
| FR-VUE-2 | `picolet dev` against a Vue app runs the Vite dev server alongside the watcher; the webview loads from `http://localhost:5173/` during dev, from `/rom/ui/` after `picolet build`. |
| FR-VUE-3 | `picolet-bridge-js` ships a TypeScript declaration file (`picolet.d.ts`) so Vue/TS apps get typed `window.picolet.invoke / on / emit` calls. |
| FR-VUE-4 | The Vue toolchain integrates with the existing `picolet build` pipeline without requiring an extra subcommand — `picolet build` detects the Vue project (via `package.json` + `vite.config.ts` presence), runs `npm run build`, and packs the resulting `dist/` into romfs at the configured root. |
| FR-VUE-5 | `picolet.toml` gains a `[ui.frontend]` table allowing `framework = "vue" \| "react" \| "vanilla"` plus a `build_cmd` override. Default is `vanilla` for back-compat with v1 templates. |

### Examples

| ID | Requirement |
|---|---|
| FR-EX-1 | `picolet init <name> --template pydfu` scaffolds the pydfu DFU flasher GUI. Functional end-to-end: detects DFU devices, picks a .dfu file, flashes, reports progress. |
| FR-EX-2 | `picolet init <name> --template notes` scaffolds a markdown-backed notes app. Persists to `~/.config/<app-name>/notes/` on Linux, `%APPDATA%\<app-name>\notes\` on Windows. |
| FR-EX-3 | `picolet init <name> --template config-editor` scaffolds a schema-driven config editor with TOML/YAML/JSON read+write, validation, and a load→edit→validate→save→diff confirmation flow. |
| FR-EX-4 | `picolet init <name> --template dashboard` scaffolds a system metrics dashboard with 1Hz event-push from Python and live charts (line, gauge, sparkline). |
| FR-EX-5 | Each example app ships a `tests/` directory with Playwright (webview examples) or LVGL-API (LVGL examples) integration tests verifying the documented user flow. |
| FR-EX-6 | Each example app ships `screenshots/` with auto-generated PNGs captured via `picolet test --screenshot` covering the major UI states (home, edit, error, success). |
| FR-EX-7 | The pydfu example uses the host filesystem (libusb access to /dev/bus/usb/* on Linux, WinUSB on Windows) via the runtime's `ffi` module — the same pydfu-win approach. |

### Aesthetic direction (non-negotiable; frontend-design skill applies)

Each example commits to a distinct visual personality. No "another shadcn dashboard" — these are demonstration apps that must look like real, intentional products. Direction is fixed in the phase plan, not left to per-developer interpretation.

| Example | Aesthetic | Typography | Palette |
|---|---|---|---|
| pydfu | Industrial control panel — Beckhoff/Altera-programmer feel, status LEDs, command-line tabular layouts | Display: Berkeley Mono (or PP Neue Machina); body: IBM Plex Sans | Forge orange (`#ff6b1a`) accent on near-black `#0a0c0e` matte chassis, status greens + alarm reds |
| notes | Editorial / refined — Bear, iA Writer, but with a stronger typographic point of view | Display: GT Sectra (serif); body: Söhne or Tiempos Text | Warm off-white `#f7f3ed` paper, ink `#1a1715`, single sharp red accent for unsaved/edit state |
| config-editor | Brutalist terminal — schema as concrete poetry, monospace everywhere, deliberate ASCII feel | Display: Atyp Mono (or VC Honey Mono); body: monospace throughout | Phosphor green-on-black `#0d1b0d` + `#a3ff7c`, single magenta accent for validation errors |
| dashboard | Sophisticated data-dense — Bloomberg-terminal energy but contemporary, dark, layered | Display: GT America Condensed; numerals: Roobert Mono; body: GT Walsheim | Slate `#101418` base, ice-blue `#7dd3fc` chart strokes, amber `#f59e0b` accents for warnings |

NFR-EX-AESTHETIC: every example must pass a "show me the screenshot — is it memorable?" test before its phase exits.

## Non-functional requirements

| ID | Requirement |
|---|---|
| NFR-EX-1 | Each example's app binary size ≤ 3 MiB on linux-x64-webview. Vue toolchain output is expected to add ~200-500 KB; that's the budget. |
| NFR-EX-2 | Each example must start (window visible, first interactive frame) in ≤ 1500 ms on a recent Linux laptop. |
| NFR-EX-3 | Each example's CSS does not pull in a runtime CSS framework heavier than 50 KB (gzipped). Tailwind via Vite is OK (purged); hand-crafted CSS preferred; component libraries dragging in everything are not. |
| NFR-EX-4 | Each example app's frontend code uses no external CDN at runtime. All assets ship in the romfs. |
| NFR-EX-5 | `picolet test` produces deterministic screenshots: same inputs → byte-identical PNG (modulo OS-level antialiasing where unavoidable; documented per-example). |
| NFR-EX-6 | The auto-generated screenshot gallery in each example's `screenshots/` is regenerated on every CI build (gated by `picolet test --screenshot`). Drift between code and screenshots is a CI failure. |
| NFR-TEST-1 | `picolet test` startup overhead (spawn → ready → drive available) ≤ 3 seconds per test run on linux-x64-webview. |
| NFR-TEST-2 | The CDP debugging port is bound to `127.0.0.1` only. `PICOLET_TEST_MODE` must never be enabled in release builds; the CI release pipeline asserts the variable's absence in the artefact. |

## Out of scope for v1.1

- React or Svelte toolchains. v1.1 lands Vue as the framework-of-record; other frameworks land via community templates later.
- LVGL versions of the four real apps. The four are all webview-based for v1.1; an `examples/lvgl-counter/` style demo lands as a separate, simpler example.
- Hot-reload of Python state during `picolet dev` for these examples — restart-on-change is still the model, just with Vite's HMR on the JS side during dev.
- App-store/installer packaging (still on roadmap as `picolet bundle`, post-v1.1).
- A documentation site / hosted screenshots. README + `screenshots/` per example is the deliverable; promotion comes later.
