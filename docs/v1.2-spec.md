# Picolet v1.2 Specification — macOS Support

This document is the contract for v1.2: macOS support at feature parity
with Linux and Windows across all three renderer variants (cli, webview,
lvgl) for two hardware architectures (x86_64 and arm64).

Frame inputs:
- v1 spec at [v1-spec.md](v1-spec.md) defines the framework FR/NFR.
- v1.1 spec at [v1.1-spec.md](v1.1-spec.md) defines example apps and
  test infra.
- Both PO audits are approved. v1.2 adds a new target dimension only;
  it does not revise any existing FR/NFR.

## Targets

v1.2 adds two macOS targets:

- `macos-x64` — x86_64 Darwin, built on GitHub Actions `macos-13`
  runner (Homebrew Intel).
- `macos-arm64` — Apple Silicon arm64, built on GitHub Actions
  `macos-14` runner.

Both are full deliverables. Universal binaries (fat Mach-O) are
explicitly out of scope for v1.2 — they add build complexity without
user benefit on a platform where the OS handles the routing.

## Build approach decision — native CI (Option A)

Two approaches were evaluated:

| Criterion | Option A — native CI runners | Option B — osxcross cross-compile |
|---|---|---|
| Apple SDK licensing | No issue — SDK stays on Apple hardware | Requires extracting Xcode SDK; redistribution is legally ambiguous even for personal use |
| Local dev builds | Not possible without macOS hardware | Possible but requires SDK extraction and osxcross setup per developer |
| CI round-trip | Required for every macOS build iteration | Can build on Linux host |
| Toolchain maintenance | GitHub maintains the runner images | osxcross + SDK version management falls on picolet |
| Binary quality | Official Apple clang; correct SDK | Cross-compiling Mach-O; known edge cases with ObjC runtime |

**Decision: Option A.** Native CI on `macos-13` and `macos-14` runners.
`picolet build --target macos-x64` and `picolet build --target macos-arm64`
reach for a CI-built artifact via the existing release resolver (D2 from
architecture.md). `picolet build --from-source` for macOS targets is
explicitly out of scope for v1.2 — it would require osxcross and cannot
be implemented without resolving the SDK licensing question.

The build script must emit a clear, actionable error when `--from-source`
is attempted for a macOS target:

```
error: --from-source for macos-* targets is not supported in v1.2.
       Use 'picolet build --target macos-x64' to download the pre-built artifact,
       or trigger a CI build manually.
```

## Functional requirements

### Runtime variants — macOS

| ID | Requirement |
|---|---|
| FR-RT-MAC-1 | Six macOS runtime artifacts ship: `macos-{x64,arm64}-{cli,webview,lvgl}`. |
| FR-RT-MAC-2 | All six artifacts are single Mach-O executables; no dylib sidecars are bundled into the artifact itself. |
| FR-RT-MAC-3 | The trailer + romfs mechanism (FR-RT-6 of v1) works identically on Mach-O. |
| FR-RT-MAC-4 | `gc.add_heap()` and `ffi` module are available in all six macOS variants (inheriting FR-RT-4, FR-RT-5 from v1). |
| FR-RT-MAC-5 | The existing unix port overlay (`overlay/ports/unix/variants/picolet-{cli,webview,lvgl}/`) serves both Linux and macOS without a Darwin-specific fork, except where explicitly noted in FR-WV-MAC or FR-LV-MAC. |

### WKWebView renderer — macOS

| ID | Requirement |
|---|---|
| FR-WV-MAC-1 | On macOS the webview variant uses WKWebView (WebKit.framework) instead of WebKitGTK. The selection is conditioned on `sys.platform == "darwin"` in the Python layer and `__APPLE__` in the C glue. |
| FR-WV-MAC-2 | A new C file `overlay/ports/unix/variants/picolet-webview/picolet_webview_mac.c` implements the macOS-specific C surface: window creation (NSWindow + NSView hierarchy via the ObjC runtime), WKWebView embed, JS-to-Python message passing, snapshot. |
| FR-WV-MAC-3 | All ObjC calls are made through the public `objc_msgSend` ABI (from `libobjc.dylib`) — no static link to Objective-C++ runtime. The implementation uses the same libffi `ffi.open` pattern as the Linux GTK binding. |
| FR-WV-MAC-4 | The WKWebView window opens, loads the romfs HTML, and the IPC bridge round-trips within the startup sequence. |
| FR-WV-MAC-5 | The picolet:// URI scheme is registered on a `WKURLSchemeHandler` (equivalent of WebKitGTK's `webkit_web_context_register_uri_scheme`) so sub-assets (CSS, JS, fonts) resolve from the in-process VFS. |
| FR-WV-MAC-6 | `window.picolet.invoke(cmd, args)` and `window.picolet.on(event, handler)` work on macOS via the same bridge-js bundle already frozen in the webview variant's romfs. |
| FR-WV-MAC-7 | When `PICOLET_TEST_MODE=1`, the runtime enables WKWebView remote inspection by calling `-[WKWebsiteDataStore defaultDataStore] setHTTPCookieAcceptPolicy:` and related API. The port is announced on stderr as `picolet:test-port=<N>`. WKWebView's remote inspector protocol differs from both WebKitGTK (it uses WKRP — WebKit Remote Protocol) and CDP; the AppHarness webkit path is extended to detect and connect to WKWebView's inspector. |
| FR-WV-MAC-8 | Screenshot capture on macOS uses `-[WKWebView takeSnapshotWithConfiguration:completionHandler:]` (available since macOS 10.13). The AppHarness `Page.captureScreenshot` in the webkit path calls this API via the ObjC bridge and returns the PNG bytes. |

### LVGL renderer — macOS

| ID | Requirement |
|---|---|
| FR-LV-MAC-1 | The macOS lvgl variant links SDL2 via the system `brew install sdl2` installation (dynamically, per NFR-5). |
| FR-LV-MAC-2 | The Cocoa backend of SDL2 (default on macOS) is used without modification — no SDL2 source patch is needed. |
| FR-LV-MAC-3 | The existing Linux LVGL variant's mpconfigvariant and manifest extend to macOS without a Darwin-specific fork; only the SDL2 library lookup path changes (brew prefix vs. system path). |

### Build pipeline integration — macOS

| ID | Requirement |
|---|---|
| FR-BP-MAC-1 | `picolet build --target macos-x64` resolves and downloads the pre-built artifact from the GitHub release (using the existing resolver in D5a). |
| FR-BP-MAC-2 | `picolet build --target macos-arm64` does the same for arm64. |
| FR-BP-MAC-3 | `picolet build --from-source --target macos-*` emits a clear error (see decision text above) and exits non-zero. |
| FR-BP-MAC-4 | `build-runtime.sh` gains a `macos-x64` and `macos-arm64` path that runs natively (no Docker container, no cross-compile) using whatever compiler is on PATH (`clang` on GitHub-hosted macOS runners). |
| FR-BP-MAC-5 | The macOS build path in `build-runtime.sh` is guarded by `[[ "$(uname -s)" == "Darwin" ]]`; running the script for `macos-*` on a non-Darwin host exits with an actionable error rather than proceeding incorrectly. |
| FR-BP-MAC-6 | `build-runtime.sh` for macOS emits SBOM sidecars (`<artifact>.cdx.json`) using the same `picolet_cli.sbom_gen` host-side tool used by Linux and Windows builds. |

### CI build matrix — macOS

| ID | Requirement |
|---|---|
| FR-CI-MAC-1 | `release.yml` is extended with `macos-13` (x64) and `macos-14` (arm64) runner entries in the build matrix, producing 6 new artifacts per release. |
| FR-CI-MAC-2 | The macOS CI steps install only explicitly listed Homebrew packages (`brew install libusb sdl2`) — no implicit dependency on pre-installed packages. |
| FR-CI-MAC-3 | `perf-check.yml` gains a macOS lane running on `macos-14` (arm64) measuring the same NFR-EX-2 and NFR-TEST-1 bounds as the Linux lane. Per NFR-MAC-10, this lane runs on `workflow_dispatch` and `schedule` only. |
| FR-CI-MAC-4 | All 12 macOS artifacts (6 binaries + 6 SBOMs) are uploaded to the GitHub Release per the existing `release` job logic. |
| FR-CI-MAC-5 | The `PICOLET_TEST_MODE` assertion step (NFR-TEST-2) runs identically in the macOS jobs. |
| FR-CI-MAC-6 | The first step of each macOS build job in `release.yml` runs `sw_vers && uname -m && which clang` and uploads the captured output as a CI artifact named `macos-runner-info-<runner>.txt`. This records the actual macOS version present on the runner before PH25 makes any assumptions about WKWebView inspector API availability. |

### Test infrastructure — macOS

| ID | Requirement |
|---|---|
| FR-TEST-MAC-1 | `AppHarness` autodetects the macOS webview variant from binary name (`macos-*-webview`) and routes to the webkit path. |
| FR-TEST-MAC-2 | The WebKit inspector on macOS uses WKRP (Web Inspector Remote Protocol) over WebSocket. `AppHarness` connects to it; the existing `WebKitPage` duck type (from `_webkit.py`) serves as the Page adapter without a macOS-specific fork, since the WKRP wire format is the same JSON-RPC structure as WebKitGTK's inspector. |
| FR-TEST-MAC-3 | `PICOLET_TEST_MODE=1` on macOS enables the WKWebView remote inspector and announces the port on stderr in the same format as Linux. |
| FR-TEST-MAC-4 | Screenshot capture on macOS uses the WKWebView snapshot API routed through `AppHarness.snapshot()`. `Page.captureScreenshot` calls this path. |
| FR-TEST-MAC-5 | The macOS perf-check lane uses `AppHarness` for port-announcement timing; window visibility is measured via `osascript -e 'tell application "System Events" to ...'` or `ps`-polling rather than `xdotool`. |

### Example apps — macOS

| ID | Requirement |
|---|---|
| FR-EX-MAC-1 | All four example apps (pydfu, notes, config-editor, dashboard) build and run on `macos-x64` and `macos-arm64`. |
| FR-EX-MAC-2 | pydfu uses `libusb-1.0.dylib` on macOS, installed via `brew install libusb`. The `_usb/core.py` macOS branch calls `ffi.open("libusb-1.0.dylib")` (no path prefix — dyld resolves via `DYLD_LIBRARY_PATH` or the brew-installed location `/usr/local/lib` on x64 / `/opt/homebrew/lib` on arm64). |
| FR-EX-MAC-3 | The `romfs_extract.py` helper's macOS branch returns the romfs path unchanged (same as Linux — dyld can find brew-installed dylibs without extraction). No new macOS-specific extraction path is needed. |
| FR-EX-MAC-4 | notes persists to `~/Library/Application Support/<app-name>/notes/` on macOS (XDG equivalent). |
| FR-EX-MAC-5 | config-editor schema files reside at `~/Library/Application Support/config-editor/schemas/` on macOS. |

## Non-functional requirements

| ID | Requirement |
|---|---|
| NFR-MAC-1 | `picolet-runtime-macos-{x64,arm64}-cli` binary ≤ 1 MiB (same as NFR-1). |
| NFR-MAC-2 | `picolet-runtime-macos-{x64,arm64}-webview` binary ≤ 2 MiB, excluding WebKit.framework (same as NFR-2). |
| NFR-MAC-3 | `picolet-runtime-macos-{x64,arm64}-lvgl` binary ≤ 2 MiB, excluding SDL2 dylib (same as NFR-3). |
| NFR-MAC-4 | macOS artifacts require no system Python and no Homebrew packages at runtime for the cli variant. The webview variant requires no extra packages (WebKit.framework is part of macOS). The lvgl variant requires `sdl2` from Homebrew (equivalent of the Linux `libwebkit2gtk-4.1-0` runtime dep for the webview variant). |
| NFR-MAC-5 | Startup time (window visible, first interactive frame) ≤ 1500 ms on a recent macOS machine (Apple Silicon M1 or later, or Intel Core i7-class). Measured in CI on `macos-14`. |
| NFR-MAC-6 | No code signing or notarisation in v1.2. Unsigned binaries will be quarantined by Gatekeeper. The workaround for users (`xattr -d com.apple.quarantine <binary>` or Security & Privacy System Preferences) is documented in `docs/macos-unsigned.md`. Code signing and notarisation are deferred to v1.3. |
| NFR-MAC-7 | The macOS webview variant does not require any third-party framework beyond `WebKit.framework` (which is bundled with macOS). No Chromium or Electron is required. |
| NFR-MAC-8 | No GPL or AGPL components are statically linked into any macOS runtime variant (inheriting NFR-5 from v1). LGPL components reached dynamically are permitted and recorded in the SBOM. |
| NFR-MAC-9 | Minimum macOS deployment target is 11.0 (Big Sur). `MACOSX_DEPLOYMENT_TARGET=11.0` is set in the macOS build path of `build-runtime.sh` and applies to both x64 and arm64. This covers all Apple Silicon hardware (arm64 requires macOS 11+) and all Intel Macs still supported by Apple at v1.2 ship date. |
| NFR-MAC-10 | The `perf-check.yml` macOS lane runs only on `workflow_dispatch` and `schedule` (weekly) triggers. It does NOT run on push or pull_request. Rationale: `macos-14` runners cost approximately 10× `ubuntu-latest` per minute; adding the macOS lane to every push would make the perf gate economically impractical. The `release.yml` macOS build jobs run only on release tags for the same reason. |

## Out of scope for v1.2

- Universal (fat) Mach-O binaries — separate per-arch artifacts only.
- `picolet build --from-source` for macOS targets (requires osxcross; SDK licensing unresolved).
- Code signing and notarisation (deferred to v1.3).
- App bundle (`.app`) / DMG packaging (deferred to `picolet bundle` roadmap).
- macOS-specific system tray integration or dock behaviour.
- iOS, tvOS, watchOS targets.
- ARM Linux targets.
- `picolet dev` Vite HMR on macOS (should work without changes but is not an explicit v1.2 test gate).
