### Proposed baseline and gating policy (for decision)

Nothing below is in effect; scans remain report-only until the user decides.

- **Baseline form:** a checked-in file keyed by rule id, repository path, and a normalised code fingerprint (not line number, since the resolver finding already moved), with a disposition (`false-positive`, `accepted-risk`, `upstream-open`) and a link to the review row. Engine limitations (parser notifications, interfile depth, Pyrefly / Pysa coverage) are listed separately as coverage gaps, never as accepted findings.
- **New findings:** a finding absent from the baseline fails the default `opengrep-stable` PR job for Picolet-owned paths. For upstream / frozen-dependency paths (`micropython/`, micropython-lib) it is reported but does not fail, because those changes arrive via submodule bumps and need routing to their owner.
- **Incomplete analysis:** a parse-error or partial-analysis count higher than the baseline's for the same cell is reported as a coverage regression. Whether that should fail the job needs a measured noise level first; the Intel WebView 42 to 43 change shows it isn't stable yet.
- **Optional scanners** (alpha, Semgrep CE, Ruff `S`, Pyrefly, Pysa) stay report-only regardless.
- **Upstream fd leak:** reproduce on macOS (for example by forcing `read` failure), then fix with an mbm feature branch that closes `fd` before raising, and decide separately whether to submit it upstream.
