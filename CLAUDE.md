# Agent Instructions

This repo is being built under autonomous agent execution. The
agent loop is the `software:spec-driven-agent-scrum` orchestrator
running over [docs/v1-spec.md](docs/v1-spec.md) and
[docs/v1-plan.md](docs/v1-plan.md).

## Branch policy

- `main` is the curated release branch. Do not commit to it directly.
- `dev` is where the loop runs. All phase work lands on `dev`.
- Phase work is **not** branched per-phase. Sequential commits on
  `dev` with descriptive messages serve the same purpose without
  merge noise.
- The `dev` history will be refined (rebase / squash per phase)
  before any future merge to `main`. Don't pre-emptively squash.

## Commit policy

- Sign every commit with `-s`.
- Subject line: imperative, ≤ 70 characters, no trailing period.
- Body: present-tense description of *why* the change is needed and
  *what* it changes at a level a reviewer needs. Reference the phase
  (e.g. `[PH06]`) and the FR / NFR ids the commit closes against.
- No emoji. No "🤖 Generated by ..." footer.
- Multiple small commits per phase are preferred over one giant
  end-of-phase commit. The phase boundary is signalled by commit
  *messages* referencing the phase id, not by a separate merge.

Example:
```
[PH01] Add picolet-cli unix variant baseline.

Lays down the lean mpconfigvariant for the linux-x64 cli runtime,
following the pydfu variant pattern. Disables compiler, REPL, json,
re, deflate, hashlib, uctypes; enables gc.add_heap and ffi.

Closes: FR-RT-3, FR-RT-4, FR-RT-5.
```

## Dev branch as investigation log

The `dev` branch doubles as the engineering notebook for the build-out
period. Anything worth remembering — a working approach, a dead end, a
non-obvious constraint surfaced by experimentation, a decision between
two options — lands as a commit on `dev` with the detail in the
message body. No separate markdown log file.

Empty commits are first-class for log entries that have no code change
attached:

```
git commit --allow-empty -s -m "[PHnn] Note: ..." -m "<body...>"
```

Subject conventions for log-only commits:

- `[PHnn] Note: <observation>` — fact, measurement, dead end documented.
- `[PHnn] Decision: <choice>` — alternative chosen, with rationale in body.
- `[PHnn] Caveat: <gotcha>` — non-obvious constraint surfaced.

The body carries the engineering content. Why it came up, what was
tried, what worked or didn't, what the implication is for later
phases. Treat it the way you would a notebook entry.

Why this shape rather than a growing markdown log file:

- `git log --oneline` is a queryable date + heading index; `git show
  <sha>` pulls full detail on demand. The index stays compact.
- The note lives next to the code state it concerns. `git log -p` over
  a phase range surfaces both the work and the reasoning together.
- A markdown log file accumulates conflict-prone edits and grows
  unbounded; commits don't.

When in doubt, write the empty commit. Future-you reading `git log`
will thank present-you.

## Build and test policy

- Host is WSL2 on Windows 11. Linux builds run natively; Windows
  builds run via dockcross MinGW cross-compile.
- Every phase that touches code must end with at least one Linux build
  and at least one Windows build green before its exit gate is
  checked, except where the phase scope is explicitly single-platform.
- Windows binaries are tested by running the `.exe` directly from WSL
  via interop (`./build/foo.exe`) — stdout returns to the WSL shell.
  This is the standard test path for Windows artefacts; no extra
  emulation needed.
- Tests live under `tests/` per package. Per-phase tests during the
  build-up phase live under `tests/phase-NN/` until reorganised.
- macOS is out of scope for v1. Do not add macOS code, CI matrix
  entries, or guards.

## Model tier defaults

- `opus` — planning, acceptance, complex C / FFI work, anything
  cross-cutting.
- `sonnet` — bulk implementation, test authoring, validation.
- `haiku` — lookups, formatting, trivial scaffolding.

Per-phase recommendations are in [docs/v1-plan.md](docs/v1-plan.md).

## Phase files

`scrum-planner` writes phase files to `docs/phases/PHASE_NN_<slug>.md`.
The `<slug>` matches the phase title in `v1-plan.md`. Subsequent roles
(developer, sqe, tester) append their progress sections to the same
file rather than creating new files.

## Escalation

If a phase cannot be implemented as planned without violating the spec
or another FR, the agent **stops**, writes the conflict into the phase
file's `## Blockers` section, and surfaces to the user. The agent does
not silently restructure the spec or the plan.

A spec change requires an explicit user decision and lands as a new
commit to `docs/v1-spec.md` before the affected phase resumes.

## Dependency policy

- All Picolet-authored code is MIT.
- Static linking of GPL or AGPL components is forbidden anywhere in
  any runtime variant (NFR-5).
- New native dependencies must be declared in
  `packages/picolet-runtime/sbom/runtime.toml` before they enter a build
  (this file is created in PH13; until then, new dependencies are
  noted in the phase file and ratified retroactively).
